# План: подписка, вход, админка, прогресс

Статус: **отложено** (7 октября 2026). Три решения ниже — за автором.

Цель — чтобы тренажёром мог пользоваться любой ребёнок по подписке:
родитель регистрирует ребёнка, задачи закрыты, пока автор не откроет доступ
в админке; у ребёнка — страница прогресса с сериями и наградами; у автора —
подробный прогресс каждого ученика. Оплату пока не подключаем, но модель
доступа под неё готова.

## Основа — существующее облако

Отдельную БД заводить не нужно. Уже есть Supabase: `supabase/schema.sql`,
`assets/cloud.js`, `account.html`, `teacher.html` — аккаунты взрослых,
профили учеников, синхронизация прогресса (`kv`), RLS. Расширяем его.

## 1. Схема (`supabase/schema.sql`)

- `profiles.role` += `admin`; функция `is_admin()` — админ читает и пишет всё.
- `students.status`: `pending` / `active` / `blocked`. Новый ученик —
  `pending`, задачи закрыты.
- Таблица `access (student_id, item, granted_by, granted_at, expires_at)`.
  `item`: `program:3` (программа 28 дней), `paper:gjmat24g4` (олимпиада),
  `assess:3` (замер). Мультивыбор в админке — набор строк. Будущая оплата
  (вебхук Stripe/Telr) вставляет те же строки с `expires_at`.
- Таблица `events` — журнал «решил задачу»: ученик, время, работа, номер,
  верно/неверно, секунды. В `kv` только последнее состояние, а для серий,
  наград и отчёта админу нужна история.
- RLS: родитель создаёт учеников, но `status` и `access` меняет только админ.
- Тесты — `tools/test_rls.sh`.

## 2. Вход и регистрация

- `register.html`: почта + пароль + согласие → создание ребёнка (псевдоним,
  класс) → письмо подтверждения → экран «ждём подтверждения доступа».
- Вход по паролю в дополнение к коду из письма.
- У ребёнка своей почты нет: входит под аккаунтом родителя и выбирает
  профиль (по желанию — PIN). Проще с защитой детских данных (ОАЭ, KSA).
- Уведомление автору о новой регистрации: Database Webhook → почта или
  Telegram (по желанию).

## 3. Админка (`admin.html`)

- Список родителей и детей, фильтр по статусу, поиск по почте.
- Карточка ученика: статус; дерево доступа с галочками (класс → программа,
  замер, олимпиады из `window.PAPERS`); срок; правка псевдонима и класса.
- Подробный прогресс: дни программы, результаты олимпиад, журнал ошибок,
  точность по темам (`topic`), время на задачу, тепловая карта по дням.
  Отрисовку взять из `report.html` и `teacher.html`.

## 4. Страница прогресса ребёнка (`progress.html`)

- Серия дней подряд: день засчитан, если решено ≥ 10 задач или закрыт день
  программы. Награды за 3, 7, 14, 28 дней; одна «заморозка» в неделю.
- XP = баллы за верные ответы по цене секции; уровни каждые N очков.
- Значки: первая олимпиада целиком; день без ошибок; 10 исправленных ошибок
  из журнала; «мастер темы» (≥ 90 % по теме); рекорд в таблице умножения;
  «на вырост» — решена работа 4 класса.
- Календарь активности, полоска до уровня, сильные и слабые темы.
- Награды считаются из `events` на клиенте, полученные — сохраняются в `kv`.

## 5. Насколько реально закрывать задачи

Сайт статический, `data/*.js` лежат в публичном репозитории.

- **Мягко:** закрыто только в интерфейсе. Быстро, но задачи доступны тому,
  кто откроет файлы.
- **Жёстко** (рекомендуется для подписки): платные наборы — в закрытом
  Supabase Storage, выдаются по `access`; в репозитории остаётся демо.
  Заодно закрывает риск чужого контента (история git останется).
  Затрагивает сборку `file://` и Android-приложение — отдельный этап.

## Порядок работ

1. Схема, RLS, `test_rls.sh`.
2. Регистрация, вход по паролю, экран ожидания, закрытие задач в хабе и
   `paper.html`.
3. Админка: доступ и подробный прогресс.
4. `events` и страница прогресса с наградами.
5. Перенос платных наборов в закрытое хранилище.

## Решения перед началом

1. Закрывать задачи мягко или жёстко?
2. Ребёнок входит под аккаунтом родителя (рекомендуется) или со своим логином?
3. Критерий дня для серии: 10 задач или закрытый день программы — подходит?
